# 性能审查（2026-09-29）

## 范围与结论

审查测速引擎、控制面/选点、时延探测、Wails 桥接、React 采样与图表、SQLite/设置、诊断 CLI 和构建流程。主要性能瓶颈集中在数据面；本轮修改引擎、测试、文档与 CI，不改用户已有界面工作、不新增依赖、不调整系统 TCP 参数。

目标是移除客户端对带宽的可避免限制，不承诺任意公网线路都能跑满；远端容量、运营商互联、RTT、丢包、网卡和 Wi-Fi 都可能是实际瓶颈。

## 已修复

| 问题 | 修复与验证 |
|---|---|
| 16 KiB 上传块，每次写重设 deadline | 256 KiB 共享随机块，deadline 每秒最多更新一次；同样负载所需 Write 调用约降至 1/16 |
| 多连接争用单个原子计数器 | 每连接独立并填充计数器，采样时聚合 |
| 下载完成 1 GB 文件后连接永久退出 | 完整响应结束后续开请求；用小文件连续三次下载回归模拟高速 rollover |
| 上传无限写入、超过声明 900 MB | 精确匹配 Content-Length，完成 multipart 尾部，读取成功响应后续开请求；两次连续 multipart 完整性回归 |
| 上传不读错误响应，HTTP/chunked framing 混入字节数 | 并发读拒绝响应；采用 net/http.ReadResponse 解帧，HTTP 头限制 64 KiB；只统计下载 body/上传文件负载 |
| 固定 40 ms/连接启动延迟，取消后仍有 I/O | 并发启动，DialContext + context.AfterFunc 关闭连接，退出等待 worker；32 连接取消与阻塞上下行回归 |
| 固定采样分母在调度/回调延迟后虚高速率 | 用真实单调时间计算窗口，阶段使用独立硬 deadline；220 ms 慢回调对 100 ms tick 的定速流回归 |
| 直接调用引擎可绕过设置限制 | 两个方向最多 32 连接，采样间隔 100–1000 ms（过小回默认 500 ms） |
| 完全没有有效样本仍记录成功阶段 | 零速率阶段返回地址族错误，不再生成该阶段成功结果 |

单线程模式仍然保持一个活动传输连接；默认 8 下行/4 上行不变，不擅自加大已有用户的网络负载。没有使用固定大 TCP 缓冲（这可能干扰自动调优，并夸大本地发送排队字节）。

## 本机回环对照

Windows amd64，AMD Ryzen 7 6800H，Go 1.26.8；接收端为本地 HTTP server，按**接收端读取的字节**计吞吐。相同测试夹具对原上传 worker 与新 worker 对照，每轮 2 次、每次 2 秒、重复 3 轮。

| 实现 | 各轮 receiver-Mbps | 中位数 |
|---|---|---|
| 原实现 | 2095 / 2096 / 2032 | 2095 Mbps |
| 新实现 | 2326 / 2079 / 2301 | 2301 Mbps |

本次中位数约提升 **9.8%**，但区间重叠、样本较少；250 ms 短窗口也观察到明显波动。因此这只是本机回环观察，不是统计显著性结论，更不能外推为公网提速幅度。更重要的是有限文件续传与阶段清理的确定性修复。原实现临时 benchmark 已移除，永久保留新版接收端基准：

~~~powershell
go test ./internal/engine -run '^$' -bench BenchmarkUploadWorker -benchtime=2x -count=3 -benchmem
~~~

## 后续审查发现与限制

- **控制面取消不完整**：出口查询、节点列表、排队和 ping 仍有独立超时，未全程接入用户 context；停止按钮在这些步骤可能仍需等待。本轮保证的是实际数据面及时停止。
- **节点选择不等于最大吞吐**：目前优先同运营商/位置及 TCP 可达性，没有逐节点容量赛跑；排队参数 bandwidth=200 的服务端含义未验证，不盲改令牌/排队协议。
- **统计口径**：avgTop3 是峰值口径；上传成功 Write 仍包含本机 TCP 排队数据，不能严格证明数据已离开网卡或已被服务器确认。要校验真实出口，应对照网关/NIC 计数器或自有 iperf3 接收端。
- **错误细节**：零样本阶段会失败，但各 worker 的具体 HTTP/网络错误尚未聚合展示；部分连接失败时仍可能低于容量。没有对拒绝服务无限重试。
- **前端/存储**：采样默认 2 Hz、单轮数据点有限；SQLite 在测速结束后保存，不在 I/O 热路径。前端生产主包约 933 kB（gzip 281 kB），Vite 有分包警告，主要影响启动而非网卡吞吐；本轮不重构用户正在修改的 UI。
- **协议兼容性**：仅在本地标准 HTTP/multipart 节点验证修正后的完整上传协议；未对公共服务跑满速测试，需要后续实际节点验证。

## 建议验证路径

1. 有线网络、同运营商节点，多线程、13 秒/阶段，先 16 下行 / 8 上行，再比较 32 连接，取多轮结果而非单次最高值。
2. 用至少两个节点交叉验证；记录 NIC/路由器字节计数与 CPU 占用，区分客户端、Wi-Fi、服务器和运营商瓶颈。
3. 高 RTT 链路增加连接数可能有帮助；吞吐下降时减少连接，不假定越多越好。
4. 使用自有 iperf3 服务验证出口上限，勿持续占用公共测速节点。

自动测试 workflow 在 Windows/Linux 构建前端并执行 Go 测试与 vet，Linux 额外运行 race；工作流的远端运行结果需推送后确认。
